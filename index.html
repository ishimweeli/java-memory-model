Java Memory Model and Garbage Collection

Empowering the next generation of technology leaders in Africa

1
Introduction
  • Java's automatic memory management is a key feature
  • Relieves developers from manual memory allocation/deallocation
  • Understanding the Java Memory Model is crucial for performance optimization
  • Effective memory management prevents memory leaks and OutOfMemoryErrors
2
Memory Areas in Java
  • Stack: Method invocations and local variables
  • Heap: Objects and their instance variables
  • Method Area: Class structures, static variables, method code
  • PC Registers: Thread execution state
  • Native Method Stack: Native method information
3
Stack Memory
  • Each thread has its own stack
  • Stores method calls in stack frames
  • Contains:
    • Local variables
    • Partial results
    • Method return values
  • Automatically allocated/deallocated on method entry/exit
  • Fixed size - can cause StackOverflowError
public void methodA() {
    int x = 10;            // Primitive on stack
    String name = "Java";  // Reference on stack, object on heap
    methodB();             // New frame pushed onto stack
}  // Frame popped when method completes
4
Heap Memory
  • Shared across all threads
  • All objects are created here
  • Reference variables point to objects in heap
  • Primary focus of Garbage Collection
  • Size configurable via JVM parameters:
    • -Xms: Initial heap size
    • -Xmx: Maximum heap size
// Creating objects - allocated on heap
String message = new String("Hello");
ArrayList<Integer> list = new ArrayList<>();

// JVM parameters example
// java -Xms512m -Xmx1024m MyApplication
5
JVM Heap Structure
  • Young Generation:
    • Eden Space: New objects are created here
    • Survivor Spaces (S0 & S1): Objects that survive Eden collection
  • Old Generation:
    • Objects that survived multiple young generation cycles
  • Metaspace (replaced PermGen in Java 8+):
    • Class metadata, method data, etc.
6
Object Lifecycle
1

Creation

Objects allocated in Eden space

2

Aging

Surviving objects move to Survivor spaces

3

Promotion

After surviving multiple young GC cycles, objects move to Old Generation

4

Collection

Objects without references are reclaimed by Garbage Collector

// 1. Creation - object allocated in Eden
Person person = new Person("John");

// 2-3. Objects that survive GC cycles age and may be promoted
// This happens automatically based on GC cycles

// 4. Collection - when no references remain
person = null;  // Object becomes eligible for GC
7
Garbage Collection Fundamentals
  • Automatic process that reclaims memory
  • Based on the concept of reachability
  • Unreachable objects (without references) are eligible for GC
  • Key processes:
    • Mark: Identify live objects
    • Sweep: Remove dead objects
    • Compact: Defragment memory (in some collectors)
8
Garbage Collection Triggers
  • Young Generation Full: Eden space fills up
  • Major Collection: Old Generation fills up
  • System.gc(): Suggestion to run GC (not guaranteed)
  • OutOfMemoryError: Last-ditch attempt before failure
// Creating many objects - may trigger Young GC when Eden fills
for (int i = 0; i < 100000; i++) {
    new byte[1024];  // Creating many short-lived objects
}

// Explicitly suggesting GC (not recommended in production)
System.gc();  // Not guaranteed to run immediately or at all
9
GC Algorithms: Serial Collector
  • Single-threaded collector
  • Freezes all application threads during collection ("Stop the World")
  • Simple and with low overhead
  • Suitable for:
    • Small applications
    • Systems with limited CPU resources
  • Specified with: -XX:+UseSerialGC
10
GC Algorithms: Parallel Collector
  • Multi-threaded Young Generation collection
  • Parallel Old GC for Old Generation
  • Still causes "Stop the World" pauses
  • Better throughput for multi-core systems
  • Suitable for:
    • Batch processing applications
    • Applications that can tolerate pauses
  • Specified with: -XX:+UseParallelGC
11
GC Algorithms: Concurrent Mark Sweep (CMS)
  • Low-pause collector
  • Collects Old Generation concurrently with application
  • Reduces pause times but with CPU overhead
  • Can suffer from heap fragmentation
  • Suitable for:
    • Interactive applications
    • Applications requiring responsive UIs
  • Specified with: -XX:+UseConcMarkSweepGC (deprecated in Java 9+)
12
GC Algorithms: G1 (Garbage First)
  • Region-based garbage collector
  • Divides heap into equal-sized regions
  • Focuses collection on regions with most garbage first
  • Balanced approach for both throughput and latency
  • Default in Java 9+
  • Suitable for:
    • Large heaps (>4GB)
    • Applications needing predictable pause times
  • Specified with: -XX:+UseG1GC

// Taking a heap dump programmatically
import java.lang.management.ManagementFactory;
import com.sun.management.HotSpotDiagnosticMXBean;

public class HeapDumper {
    public static void dumpHeap(String filePath) throws Exception {
        HotSpotDiagnosticMXBean mxBean = ManagementFactory.getPlatformMXBean(
                HotSpotDiagnosticMXBean.class);
        mxBean.dumpHeap(filePath, true);
        System.out.println("Heap dumped to " + filePath);
    }
}

Common Memory Problems
  • Memory Leaks: Objects referenced but not used
  • High Allocation Rate: Creating too many short-lived objects
  • Premature Promotion: Objects promoted to Old Gen too quickly
  • Long GC Pauses: Application unresponsive during collection
  • OutOfMemoryError: Heap exhaustion or Metaspace limits
// Memory leak example - forgetting to close resources
public void processFile() throws FileNotFoundException {
    FileInputStream fis = new FileInputStream("data.txt");
    // Read data...
    // Missing fis.close() - resource leak
}

// OutOfMemoryError example
List<byte[]> list = new ArrayList<>();
while(true) {
    list.add(new byte[1_000_000]); // Continuous allocation
}
17
Memory Optimization Strategies
  • Object Pooling: Reuse objects instead of creating new ones
  • Weak/Soft References: Allow GC to collect when memory is tight
  • Collection Sizing: Use appropriate initial collection sizes
  • Immutable Objects: Reduce garbage from object modifications
  • Proper Heap Configuration: Right-size Young vs Old Generation
// Object pooling example
class ConnectionPool {
    private List<Connection> pool = new ArrayList<>(10);
    
    public Connection getConnection() {
        if (pool.isEmpty()) {
            return new Connection();
        }
        return pool.remove(pool.size() - 1);
    }
    
    public void releaseConnection(Connection conn) {
        pool.add(conn);  // Return to pool instead of being garbage collected
    }
}

// Weak reference example
WeakReference<LargeObject> weakRef = new WeakReference<>(largeObject);
// GC can collect largeObject even if weakRef exists
18
JVM Tuning Parameters
  • -XX:NewRatio: Ratio of Old/Young Generation sizes
  • -XX:SurvivorRatio: Ratio of Eden/Survivor space sizes
  • -XX:MaxGCPauseMillis: Target for maximum GC pause time
  • -XX:ParallelGCThreads: Number of GC threads to use
  • -XX:ConcGCThreads: Number of threads for concurrent phases
# Complete JVM startup with tuning parameters
java -Xms2g -Xmx2g \
     -XX:NewRatio=3 \
     -XX:SurvivorRatio=6 \
     -XX:+UseG1GC \
     -XX:MaxGCPauseMillis=200 \
     -XX:ParallelGCThreads=4 \
     -XX:ConcGCThreads=2 \
     -jar MyApplication.jar

Best Practices
